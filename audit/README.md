# 監査プロトコル

Claude Code on the Web のように **人間がローカルでコードを実行できない環境** において、
成果物の品質責任を人間が保持するための手続き。

## 前提となる考え方

ローカル開発における人間の品質保証は、次の 3 つの行為に分解できる。

1. **読む**（コードを目で追う）
2. **動かす**（実行して挙動を確かめる）
3. **触る**（対話的に条件を変えて探索する）

Web 環境では 2 と 3 を人間が直接行えない。したがって、
**「人間が行う探索」を「機械が行う全数照合」に置き換え、人間は判断だけを担う** 形に再設計する。

人間が読むべき対象は、実装全文ではなく次の 3 点に絞られる。

- `SPEC.md` — 正典。人間が承認する唯一の意思決定。
- `audit/oracle.mjs` — 仕様を実装から独立に書き起こしたもの（約 40 行）。
- 監査レポートの **差分表** — 実装と仕様が食い違った箇所だけ。

## 4 つの監査チャネル

| # | チャネル | コマンド | 何を保証するか |
|---|---|---|---|
| ① | 単体テスト＋カバレッジ | `npm run test:coverage` | 開発者の意図どおりに動くこと（**仕様との一致は保証しない**） |
| ② | 状態空間スクリーンショット行列 | `npm run audit:shots` | 人間が目視で最終判断できる証跡を残すこと |
| ③ | 仕様オラクル全数差分照合 | `npm run audit:spec` | 実装が **仕様** と一致すること（768 ケース） |
| ④ | UI 実描画 × 仕様照合 | `npm run audit:ui` | 表示層を含めて仕様と一致すること（324 ケース） |

一括実行:

```bash
npm run audit
```

## 監査チャネルの独立性

③ と ④ が有効なのは、`audit/oracle.mjs` が `src/rules.mjs` を **参照していない** ためである。
両者が同じ誤解を共有した瞬間に、この監査は無価値になる。したがって次を不変条件とする。

- オラクルの根拠は `SPEC.md` の条文のみとする。実装を見て書いてはならない。
- オラクルを実装に合わせて修正することを禁止する。差分が出た場合、
  疑うべきは常に「実装」か「仕様の記述」であり、オラクルではない。
- 仕様が変わったときは、`SPEC.md` → オラクル → 実装 の順に更新する。

## 実測された検出力

本リポジトリに 3 件の欠陥（境界値の等号誤り / 仕様解釈の誤り / 表示層のみの丸め）を
仕込んだ状態で各チャネルを実行した結果:

| 欠陥 | ① 単体テスト | ② 目視 | ③ 仕様照合 | ④ UI 照合 |
|---|---|---|---|---|
| D1 `>` と `>=` の取り違え | ❌ 見逃し | ✅ 検出 | ✅ 検出 | ✅ 検出 |
| D2 R5 の仕様解釈誤り | ❌ 見逃し | ✅ 検出 | ✅ 検出 | ✅ 検出 |
| D3 表示層の千円丸め | ❌ 見逃し | ✅ 検出 | ❌ 対象外 | ✅ 検出 |

単体テストは **13 件全パス・分岐カバレッジ 100%** の状態で 3 件すべてを見逃した。
カバレッジは品質の指標ではない。
