# PRD: task-cli

## Executive Summary

`task-cli` は、人間と AI エージェントが**同一の Markdown ファイル**を通じてタスクリストを共有するためのコマンドラインツールである。データストアは専用フォーマットではなく、GitHub でそのままレンダリングされる Markdown のチェックリストとする。これにより、人間はエディタで直接編集でき、AI エージェントは追加のツール導入なしにファイルを読んで文脈を得られる。

CLI は `add` / `list` / `done` / `rm` の 4 コマンドを提供し、優先度・タグ・期限による絞り込みをサポートする。Python 標準ライブラリのみで実装し、依存はテスト用の pytest に限る。

## Problem Statement

AI エージェントと人間が協働するとき、タスクの所在が分かれる。

- 人間側のタスクは Jira / Linear / GitHub Issues のような **API 越しにしか読めない場所**にある。エージェントがそれを読むには認証・ネットワーク・ツール導入が要り、環境によっては到達できない（実際、本リポジトリのクラウドセッションでは `gh` CLI が API ゲートで 403 になる）。
- エージェント側が作るタスクリストは、セッション内のメモリやアドホックなファイルに散らばり、**人間がレビューできる形で残らない**。

結果として、同じプロジェクトについて人間の見ているリストとエージェントの見ているリストが乖離する。片方が完了したタスクをもう片方が再着手する、片方だけが知っている制約が実装に反映されない、といった手戻りが起きる。

必要なのは、**両者が前提なしに読み書きできる単一の置き場所**である。Markdown ファイルはその条件を満たす。git で版管理でき、レビュー時に diff として現れ、エージェントは `Read` するだけで全体を把握でき、人間はエディタで直接直せる。CLI はその Markdown を壊さずに操作するための薄い層として存在する。

## User Stories

### US-1: 開発者がターミナルを離れずにタスクを記録する

**As a** 開発中の開発者
**I want to** 思いついたタスクを 1 コマンドで記録する
**So that** 作業中のコンテキストを失わずに済む

**Acceptance Criteria:**
- [ ] `task add "リファクタする"` でタスクが追加され、割り当てられた ID が標準出力に表示される
- [ ] `--priority` / `--tag` / `--due` を省略した場合も成功し、優先度は既定値 `mid` になる
- [ ] 追加後、タスクファイルが Markdown のチェックリストとして妥当な状態を保っている
- [ ] タスクファイルが存在しない場合は自動生成される（初期化コマンドを別途叩く必要がない）

### US-2: AI エージェントが人間の作ったタスクを読む

**As a** リポジトリ上で作業する AI エージェント
**I want to** タスクファイルを追加ツールなしで読める
**So that** 認証やネットワーク到達性に依存せず作業の前提を把握できる

**Acceptance Criteria:**
- [ ] タスクファイルは有効な Markdown であり、GitHub 上でチェックリストとしてレンダリングされる
- [ ] メタデータ（優先度・タグ・期限）が Markdown の可読性を壊さない記法で埋め込まれている
- [ ] CLI を通さずエディタで手編集したファイルを、CLI が引き続き読める
- [ ] 手編集で壊れた行があった場合、CLI は全体を異常終了させず、壊れた行のみ警告して残りを処理する

### US-3: 今やるべきタスクだけを見る

**As a** 多数のタスクを抱えた開発者
**I want to** 優先度・タグ・期限でリストを絞り込む
**So that** 一覧が長くなっても着手対象を即座に選べる

**Acceptance Criteria:**
- [ ] `task list` は未完了タスクのみを表示する
- [ ] `task list --all` は完了済みを含めて表示する
- [ ] `task list --priority high` は優先度 high のみを表示する
- [ ] `task list --tag docs` は当該タグを持つタスクのみを表示する
- [ ] 複数のフィルタを同時指定した場合は AND で結合される
- [ ] 表示順は優先度の降順（high → mid → low）、同一優先度内では期限の昇順、期限なしは末尾

### US-4: 期限切れを見落とさない

**As a** 期限のあるタスクを持つ開発者
**I want to** 期限切れのタスクが一覧上で明確に区別される
**So that** 対応漏れに気づける

**Acceptance Criteria:**
- [ ] `--due 2026-08-20` の形式で期限を設定できる
- [ ] 期限が本日より前かつ未完了のタスクは、一覧で `OVERDUE` として明示される
- [ ] 期限が本日のタスクは `DUE TODAY` として区別される
- [ ] 不正な日付形式（`2026-13-45` や `tomorrow` など）は、その場でエラーを返しファイルを変更しない
- [ ] `task list --overdue` で期限切れのみを抽出できる

### US-5: 完了と削除を取り違えない

**As a** タスクを消化する開発者
**I want to** 完了と削除が別コマンドとして存在する
**So that** 完了履歴を残しつつ、誤登録だけを取り除ける

**Acceptance Criteria:**
- [ ] `task done <id>` はタスクをチェック済みに変え、ファイルからは消さない
- [ ] `task rm <id>` はタスクを行ごと削除する
- [ ] 存在しない ID を指定した場合、両コマンドとも非ゼロ終了し、ファイルを変更しない
- [ ] すでに完了しているタスクに `done` を実行した場合、警告を出すがエラーにはしない（冪等）

## Functional Requirements

| # | 要件 |
| --- | --- |
| FR-1 | `add <text>` — タスクを追加する。オプション: `--priority {high,mid,low}`（既定 `mid`）、`--tag <tag>`（複数指定可）、`--due YYYY-MM-DD` |
| FR-2 | `list` — タスクを一覧表示する。オプション: `--all`、`--priority`、`--tag`、`--overdue` |
| FR-3 | `done <id>` — タスクを完了状態にする |
| FR-4 | `rm <id>` — タスクを削除する |
| FR-5 | ID はタスク追加時に採番される。既存タスクの ID は、他のタスクが削除されても変化しない |
| FR-6 | データストアは単一の Markdown ファイル。既定パスは `./TASKS.md`、環境変数 `TASK_CLI_FILE` で上書き可能 |
| FR-7 | 保存形式は GitHub Flavored Markdown のタスクリスト（`- [ ]` / `- [x]`）を基本行とする |
| FR-8 | 不正な行を含むファイルを読んだ場合、当該行を標準エラーに警告して読み飛ばし、正常な行の処理を継続する |
| FR-9 | すべてのコマンドは成功時 0、利用者起因のエラー時に非ゼロで終了する |

## Non-Functional Requirements

| # | 要件 |
| --- | --- |
| NFR-1 | 実行時の依存は Python 標準ライブラリのみ。開発時のみ pytest を許容する |
| NFR-2 | Python 3.10 以上で動作する |
| NFR-3 | ファイル書き込みは一時ファイルへ書いてから `os.replace` で置換する。書き込み中に中断されても元ファイルが破損しない |
| NFR-4 | タスク 1000 件のファイルに対し、`list` が 1 秒以内に完了する |
| NFR-5 | CLI が書き出した Markdown は、CLI を介さず人間が読んで理解でき、手編集できる |

## Success Criteria

完了と判定する条件は次の 4 つすべてを満たすこととする。

1. **テストが全件パスする** — `python -m pytest` が失敗 0 件で終了する
2. **主要コマンドが実際に動く** — クリーンな一時ディレクトリで `add` → `list` → `done` → `list --all` → `rm` を順に実行し、各ステップで期待する標準出力と終了コードが得られることを、実際のターミナル実行で確認する
3. **受け入れ基準の充足** — US-1 〜 US-5 のすべての Acceptance Criteria にそれぞれ対応するテストが存在し、パスしている
4. **手編集との往復** — CLI が生成した `TASKS.md` を手で編集（行の追加・並べ替え）した後も、`list` が全タスクを正しく読めることを確認する

## Constraints & Assumptions

**制約**
- 実行時依存は Python 標準ライブラリのみ（NFR-1）。`typer` や `rich` は使用しない
- 開発は Claude Code のクラウドセッション上で行う。`pip install` はプロキシ経由となるため、pytest 以外の追加インストールを前提にしない
- 本 PRD は CCPM の検証題材でもあるため、タスクは 5〜8 件に分解でき、うち複数が並列実行可能であることが望ましい

**前提**
- 利用者はターミナルの基本操作ができる
- タスクファイルは git 管理下に置かれ、履歴とコンフリクト解決は git に委ねる
- 単一ユーザーが単一マシンから操作する。同時書き込みの排他制御は行わない

## Out of Scope

以下は本 PRD では**実装しない**。

- **カラー出力および TTY 判定** — 出力は常にプレーンテキストとする（ブレストで明示的に対象外とした）
- **タスクの編集コマンド** — 追加後の本文・優先度・期限の変更は、Markdown を手編集して行う
- **サブタスク・階層構造** — タスクはフラットなリストとする
- **繰り返しタスク・リマインダー・通知**
- **複数ファイル / プロジェクト横断の集計**
- **同時書き込みのロック機構** — 前提のとおり単一ユーザーを想定する
- **GitHub Issues など外部トラッカーとの同期**
- **週次レポート生成** — ブレストで選択されなかった

## Dependencies

**外部依存**
- Python 3.10 以上（実行環境に既存）
- pytest（テスト実行時のみ）

**内部依存**
- なし。本リポジトリの既存コードに依存しない新規コンポーネントである

**このプロジェクトに依存するもの**
- なし
