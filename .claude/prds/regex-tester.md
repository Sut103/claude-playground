# PRD: regex-tester

## Executive Summary

正規表現を書く人が、パターンとテスト文字列を入力してその場で挙動を確かめられる単一ページアプリを作る。マッチ箇所のハイライト、キャプチャグループの一覧、置換結果のプレビューをリアルタイムに返し、使ったパターンは履歴として端末に残る。

差別化点は 2 つある。ひとつはインストールもビルドも不要なこと — HTML ファイルをブラウザで開けば動く。もうひとつは、破綻的バックトラッキングを起こすパターンを入力しても UI が固まらないこと。マッチの実行を Web Worker に隔離し、規定時間を超えたら worker ごと打ち切る。

## Problem Statement

正規表現は「書いてみないと分からない」言語である。`\d+` が期待通り動くかは頭の中では確定せず、実際の入力に当ててみる必要がある。しかし現状の確認手段にはそれぞれ問題がある。

- **ブラウザの devtools コンソール** — `str.match(/.../)` を毎回打ち直す必要があり、フラグを変えて試す、キャプチャの中身を見る、といった反復が煩雑。マッチ位置は目で数えることになる。
- **既存のオンラインツール** — 高機能だが、パターンとテスト文字列を外部サーバに送信する。業務ログや個人情報を含む文字列を貼るのは躊躇われる。
- **エディタの検索機能** — 置換のプレビューはできても、キャプチャグループの中身やマッチのインデックスは見えない。

さらに、正規表現テスターを自作する場合に必ず踏む地雷がある。`(a+)+$` のようなパターンに長い非マッチ文字列を当てると、`String.prototype.match` がメインスレッドを占有してタブごと応答不能になる。入力のたびに評価するリアルタイム UI では、**ユーザがタイプしている途中の未完成なパターンが偶然この形になる**ため、避けて通れない。

## User Stories

### US-1: パターンの挙動をその場で確かめる

> 正規表現を書いている開発者として、パターンとテスト文字列を入力したら、どこがマッチしたかを即座に目で見たい。期待と違う箇所が一目で分かるように。

**受け入れ基準**
- パターン欄とテスト文字列欄に入力すると、追加操作なしにマッチ結果が更新される
- マッチした部分文字列がテスト文字列上で背景色によって強調される
- 隣接する複数マッチが視覚的に区別できる（交互に色を変える等）
- マッチが 0 件のときは「マッチなし」と明示される
- パターンが構文的に不正なとき、エラー内容が表示され、直前の有効な結果でハイライトが固まらない

### US-2: フラグを切り替えて挙動差を見る

> 正規表現を書いている開発者として、`g` や `i` や `m` を付け外ししたときの結果の変化を見たい。フラグの意味を実例で理解できるように。

**受け入れ基準**
- `g` `i` `m` `s` `u` `y` の各フラグを個別にトグルできる
- トグルすると即座に結果が再計算される
- 現在のフラグ構成が `/pattern/gim` の形で確認できる
- `u` フラグ有効時に不正なエスケープを含むパターンは、エラーとして報告される

### US-3: キャプチャグループの中身を確認する

> パターンから値を抽出したい開発者として、各マッチがどのグループに何を捕捉したかを一覧で見たい。抽出コードを書く前に取り出せる値を確定できるように。

**受け入れ基準**
- マッチごとに、マッチ全体・各グループ・マッチ開始インデックスが表形式で表示される
- 番号付きグループは番号（1, 2, ...）で、名前付きグループは名前で識別される
- マッチしなかったオプショナルグループは、空文字列と区別できる形で表示される（`undefined` の明示）
- `g` フラグなしのときは 1 件目のみ、ありのときは全件が並ぶ

### US-4: 置換結果をプレビューする

> ログを一括整形したい開発者として、置換文字列を入れた結果を実行前に見たい。破壊的な一括置換を走らせる前に確信を持てるように。

**受け入れ基準**
- 置換文字列の入力欄があり、入力すると置換後の全文が表示される
- `$1` `$<name>` `$&` `$$` といった置換パターンが JavaScript の `String.prototype.replace` と同じ意味で解釈される
- 置換文字列が空のときは、置換プレビュー領域は結果を出さず待機状態と分かる表示になる
- 置換結果はコピー操作ができる

### US-5: 前回のパターンを引き継ぐ

> 正規表現を継続的に調整している開発者として、タブを閉じて開き直しても直前の状態から再開したい。試行錯誤の途中で失われないように。

**受け入れ基準**
- 直近に使ったパターンが、フラグとともに履歴として保存される
- 再訪時に最後の入力内容（パターン・テスト文字列・フラグ・置換文字列）が復元される
- 履歴からエントリを選ぶと、そのパターンとフラグが入力欄に適用される
- 履歴には上限があり、上限を超えた古いエントリは自動で捨てられる
- 履歴を全消去する操作がある
- 保存はブラウザ内に閉じ、ネットワーク送信は一切行われない

### US-6: 暴走パターンでも操作を続けられる

> パターンをタイプ中の開発者として、たまたま破綻的バックトラッキングを起こす形になっても、アプリが固まらないでほしい。タブを閉じて作業をやり直す羽目にならないように。

**受け入れ基準**
- マッチ処理はメインスレッド外で実行され、実行中も入力欄の操作が継続できる
- 規定のタイムアウトを超えた実行は打ち切られ、タイムアウトした旨が表示される
- タイムアウト後、ユーザがパターンを修正すれば通常どおり結果が返る（復帰に再読み込みを要さない）
- タイムアウトの発生がアプリ全体の機能不全につながらない

## Functional Requirements

**FR-1 入力** — パターン、テスト文字列、置換文字列の 3 つの入力欄と、6 種のフラグトグルを持つ。

**FR-2 評価** — 入力が変化したら、デバウンスを挟んでマッチ評価を実行する。

**FR-3 ハイライト** — テスト文字列上のマッチ範囲を強調表示する。ゼロ幅マッチ（`(?=x)` 等）は幅を持たないため、位置マーカーとして表示する。

**FR-4 キャプチャ表示** — マッチごとの全体・グループ・インデックスを表として描画する。

**FR-5 置換** — 置換文字列が与えられたとき、置換後の全文を生成して表示する。

**FR-6 エラー報告** — 不正なパターンは `RegExp` のコンストラクタエラーを人間可読な形で表示する。

**FR-7 履歴** — パターンとフラグの組を localStorage に保存し、一覧・再適用・全消去ができる。

**FR-8 実行隔離** — マッチと置換の実行は Web Worker 内で行い、タイムアウトを超えたら `terminate()` して新しい worker を用意する。

## Non-Functional Requirements

**NFR-1 依存ゼロ** — 実行時の外部依存を持たない。npm パッケージもCDNも使わない。

**NFR-2 ビルドレス** — トランスパイルやバンドルの工程を持たない。ソースを直接ブラウザが読む。

**NFR-3 オフライン完結** — 起動後にネットワーク通信を行わない。入力内容が端末外に出ない。

**NFR-4 応答性** — 通常のパターンに対し、入力停止から結果表示まで体感で遅延を感じない範囲に収める。

**NFR-5 テスト可能性** — ロジック層は DOM に依存しない ES モジュールとして切り出し、`node --test` で実行できる。

**NFR-6 安全な描画** — テスト文字列はユーザ入力であり、HTML として解釈させない。

## Success Criteria

1. `index.html` をブラウザで直接開いて全機能が動作する（サーバ起動やビルド手順を要さない）
2. `node --test` が追加インストールなしに実行でき、全テストが通る
3. ロジック層（マッチ・置換・履歴・ハイライト範囲計算）の関数が単体テストで覆われている
4. `(a+)+$` に 30 文字以上の非マッチ文字列を当てても、UI がタイムアウト表示を返して操作可能なままである
5. `<script>alert(1)</script>` をテスト文字列に入れてもスクリプトが実行されない
6. `package.json` の `dependencies` と `devDependencies` がいずれも空、または `package.json` 自体が存在しない
7. US-1 〜 US-6 の全受け入れ基準が満たされている

## Constraints & Assumptions

**制約**
- 素の HTML / CSS / JavaScript のみ。ビルドツールを導入しない
- テストは Node 標準の `node --test` を使う。テストのために依存を追加しない
- 対象は Web Worker と ES モジュールをサポートする現行ブラウザ

**前提**
- 正規表現エンジンはブラウザ組み込みの JavaScript `RegExp` を使う。独自のエンジンは実装しない
- 利用者は正規表現の基本構文を既に知っている。文法の教育はアプリの役目ではない
- 単一利用者・単一端末での利用。同期や共有は考えない

**既知のリスク**
- `file://` 経由で開いた場合、ブラウザによっては ES モジュールと Web Worker が CORS 制約で読み込めない。この場合の起動手順を決めておく必要がある（Epic の Architecture Decisions で扱う）
- Worker はタイムアウト時に `terminate()` するため、worker の再生成コストが連続タイムアウト時に積み上がる

## Out of Scope

以下は MVP に含めない。

- **正規表現の解説・可視化** — パターンを構文木に分解して図示する機能、各トークンの意味説明
- **チートシート / リファレンス** — 構文の一覧表示
- **他言語方言への対応** — PCRE、Python `re`、Go `regexp` 等の差異吸収。JavaScript の `RegExp` のみを対象とする
- **パターンの共有** — URL へのエンコード、サーバ保存、リンク生成
- **複数タブ / 複数パターンの同時比較**
- **テスト文字列のファイル読み込み** — ドラッグ&ドロップやファイル選択
- **マッチ結果のエクスポート** — CSV / JSON 出力
- **静的な ReDoS 検出** — パターンを解析して危険性を事前警告する機能。実行時タイムアウトのみで対処する
- **ダークモード以外のテーマ切り替え・国際化**

## Dependencies

**外部依存** — なし。実行時・テスト時ともに追加パッケージを要しない。

**プラットフォーム依存**
- ブラウザの `RegExp` 実装（マッチ・置換のセマンティクス）
- `Worker` API（実行隔離）
- `localStorage` API（履歴の永続化）
- Node.js の `node --test`（テスト実行）

**内部依存** — なし。既存コードベースは README のみで、再利用できる資産はない。
