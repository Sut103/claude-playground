# PRD: regex-tester

## Executive Summary

開発者が JavaScript の正規表現を「コードに埋める前に」検証するための、依存ゼロ・ビルド不要のブラウザ単体アプリ。パターンとテスト文字列を入力すると、マッチ範囲が即座にハイライトされ、キャプチャグループが表に展開される。フラグは個別に切り替えられ、置換文字列を与えれば `String.prototype.replace` の結果をプレビューできる。入力内容は localStorage に保存され、リロード後も復元される。

単一の HTML を `file://` で開くだけで動作し、サーバもネットワークもパッケージインストールも不要。ブラウザの `RegExp` の挙動そのものを正とするため、テスターの結果と本番コードの結果が乖離しない。

## Problem Statement

正規表現を書くとき、開発者は挙動を確かめるために devtools の console を開き、`/pattern/g` と対象文字列を毎回タイプし、`match()` や `exec()` のループを手で書いている。この方法には具体的な問題がある。

1. **マッチ位置が目で見えない。** `exec()` の戻り値は `index` と部分文字列であって、元の文字列のどこが拾われたのかを視覚的に把握できない。「意図した範囲より 1 文字多く食っている」類のバグを見落とす。
2. **グループの対応が読み取れない。** 番号付きグループと名前付きグループが混在すると、配列インデックスと `groups` オブジェクトを目で突き合わせる作業になる。
3. **毎回タイプし直す。** console はリロードで消える。同じパターンを何度も打ち直す。
4. **フラグの影響を比較しづらい。** `g` の有無で `exec()` の挙動が変わる、`m` で `^` の意味が変わる、といった差分を確かめるには、その都度コードを書き換える必要がある。
5. **既存のオンラインツールは信用しづらい。** 多くは PCRE など別方言のエンジンで動いており、ブラウザの `RegExp` と結果が一致しない。加えて、業務で扱う文字列を外部サービスに貼るのは避けたい。

外部サービスに送信せず、ブラウザ自身の `RegExp` で評価し、結果を視覚化する手元のツールがあればこれらは全て解消する。

## User Stories

### US-1: マッチ範囲を目で確かめる

開発者として、パターンを入力したら、テスト文字列上のどこがマッチしたのかを色で見たい。意図より広く/狭く拾っていることに即座に気付けるから。

**受け入れ条件**
- パターン入力欄に文字を打つと、明示的な実行操作なしにハイライトが更新される
- マッチした部分文字列が背景色付きで表示され、マッチしていない部分は通常表示のまま
- 隣接する複数マッチが視覚的に区別できる（連続した 2 マッチが 1 つの塊に見えない）
- 幅ゼロのマッチ（例: パターン `a*` が空文字にマッチする位置）が、幅を持たないマーカーとして位置だけ示される
- マッチが 0 件のときは「マッチなし」と明示され、前回のハイライトが残らない

### US-2: キャプチャグループの中身を表で読む

開発者として、各マッチのキャプチャグループを表形式で見たい。番号付きと名前付きの対応を目で突き合わせる手間をなくしたいから。

**受け入れ条件**
- マッチごとに 1 行以上のエントリが表示され、各エントリに開始インデックスと全体一致文字列が含まれる
- 番号付きグループが `$1`, `$2`, ... のラベルで、対応する捕捉文字列とともに表示される
- 名前付きグループ `(?<name>...)` が `name` のラベルで表示される
- 未参加のグループ（`undefined` になるグループ）が、空文字列と区別できる形で表示される
- マッチ 0 件のとき、表は空状態のメッセージを表示する

### US-3: フラグを切り替えて挙動差を見る

開発者として、フラグを個別に ON/OFF して結果の変化を見たい。`g` の有無や `m` の効果をコード書き換えなしで確かめたいから。

**受け入れ条件**
- `g` `i` `m` `s` `u` `y` の 6 フラグを個別に切り替えられる
- `g` が OFF のとき、マッチは先頭 1 件のみになる
- `g` が ON のとき、文字列全体を走査して全マッチが列挙される
- フラグを切り替えると、明示的な実行操作なしに結果が更新される
- 現在有効なフラグが `/pattern/gimsuy` の形で表示され、実際に評価に使われた値と一致する

### US-4: 不正なパターンでも壊れない

開発者として、パターンを入力途中の壊れた状態でも画面が崩れないでほしい。`(` を打った瞬間にエラーで真っ白になると、そもそも入力ができないから。

**受け入れ条件**
- コンパイルできないパターン（例: `(`, `[`, `a{2,1}`, `\`）を入力すると、エラーメッセージが表示される
- エラーメッセージはブラウザが返す `SyntaxError` の内容を含み、何が問題かが読み取れる
- エラー中もアプリは操作可能な状態を保ち、パターンを直せば正常表示に復帰する
- エラー中はグループ表とハイライトが「結果なし」の状態になり、直前の成功結果が残って誤読を招かない

### US-5: 置換結果をプレビューする

開発者として、置換文字列を与えたときの結果を見たい。`replace()` の `$1` や `$<name>` の展開が意図通りか確かめたいから。

**受け入れ条件**
- 置換文字列の入力欄があり、入力すると置換結果が専用の領域に表示される
- `$1`〜`$9`（番号付きグループ）、`$<name>`（名前付きグループ）、`$&`（全体一致）、`$$`（リテラル `$`）が `String.prototype.replace` の仕様通りに展開される
- `g` が OFF のとき、置換は先頭 1 件のみに適用される
- 置換文字列が空のときは、マッチ部分が削除された結果が表示される
- 置換結果はプレビューのみで、テスト文字列の入力内容を書き換えない

### US-6: 入力がリロードで消えない

開発者として、パターンとテスト文字列がリロード後も残っていてほしい。うっかりタブを閉じて打ち直すのを避けたいから。

**受け入れ条件**
- パターン、テスト文字列、フラグ、置換文字列が localStorage に保存される
- ページをリロードすると、保存された 4 項目が復元され、復元直後の表示が保存前と一致する
- 保存データが存在しない初回起動時は、動作を説明するための初期サンプル（パターンとテスト文字列）が入った状態で開く
- 保存データが壊れている場合（不正な JSON 等）、例外を投げずに初期状態にフォールバックする
- 入力内容を消去して初期状態に戻す操作がある

## Functional Requirements

### FR-1: 正規表現の評価

- FR-1.1: 入力されたパターンとフラグから `RegExp` を構築し、テスト文字列に対して全マッチを列挙する
- FR-1.2: `g` または `y` が有効なときは `exec()` を反復して全マッチを収集する。無効なときは先頭 1 件のみ
- FR-1.3: 幅ゼロのマッチを検出したら `lastIndex` を 1 進めて反復を継続し、無限ループに入らない
- FR-1.4: サロゲートペアを含む文字列で `lastIndex` を進める際、`u` フラグ有効時はコードポイント単位で進める
- FR-1.5: マッチ数の上限を 10,000 件とし、超過した場合は収集を打ち切って「打ち切った」ことを表示する
- FR-1.6: 各マッチについて、開始インデックス、終了インデックス、全体一致文字列、番号付きグループ配列、名前付きグループの連想配列を保持する
- FR-1.7: パターンのコンパイルに失敗した場合、例外を捕捉してエラー情報として返す（アプリを停止させない）

### FR-2: ハイライト描画

- FR-2.1: マッチ範囲とマッチ外範囲を交互に並べたセグメント列を生成する
- FR-2.2: テスト文字列に含まれる `<`, `>`, `&`, `"`, `'` を HTML エスケープし、文字列内容が markup として解釈されないようにする
- FR-2.3: 隣接するマッチを視覚的に区別できるよう、マッチごとに独立した要素として描画する
- FR-2.4: 幅ゼロのマッチを、文字を覆わない位置マーカーとして描画する
- FR-2.5: 改行とインデント（連続空白）をテスト文字列の見た目通りに保持する
- FR-2.6: マッチ 0 件のとき、テスト文字列全体をハイライトなしで表示する

### FR-3: グループ表

- FR-3.1: 全マッチを走査し、マッチ番号、開始インデックス、全体一致を含む表を描画する
- FR-3.2: 番号付きグループを `$N` ラベルで、名前付きグループを名前ラベルで列挙する
- FR-3.3: `undefined` のグループを空文字列と区別できる表記で示す
- FR-3.4: マッチ 0 件およびエラー時に空状態メッセージを表示する

### FR-4: フラグ制御

- FR-4.1: `g` `i` `m` `s` `u` `y` を個別に切り替える UI を提供する
- FR-4.2: 有効フラグを `/pattern/flags` 形式で表示する
- FR-4.3: フラグ変更時に評価と全表示を再実行する

### FR-5: 置換プレビュー

- FR-5.1: 置換文字列の入力を受け取り、`String.prototype.replace` に委譲して結果を得る
- FR-5.2: 置換結果を HTML エスケープして専用領域に表示する
- FR-5.3: パターンがエラーのとき、置換結果領域を空状態にする
- FR-5.4: 置換結果はテスト文字列の入力値を変更しない

### FR-6: 永続化

- FR-6.1: パターン、テスト文字列、フラグ、置換文字列を localStorage の単一キーに JSON として保存する
- FR-6.2: 起動時に読み出し、各フィールドを復元する
- FR-6.3: 読み出しに失敗した場合（キー欠損、JSON パース失敗、型不一致）、初期サンプル状態にフォールバックする
- FR-6.4: localStorage が利用不可な環境（`file://` でのアクセス制限等）でも、保存失敗を捕捉してアプリの動作を継続する
- FR-6.5: 保存内容を消去して初期状態に戻す操作を提供する

## Non-Functional Requirements

### NFR-1: 性能

- NFR-1.1: 10,000 文字のテスト文字列と 1,000 件のマッチに対して、入力から描画完了までが 100ms 以内
- NFR-1.2: 幅ゼロマッチを大量に生む病的なパターン（例: `a*` を 10,000 文字に適用）でも、5 秒以内に描画が完了しブラウザが応答不能にならない

### NFR-2: 安全性

- NFR-2.1: テスト文字列・パターン・置換文字列に含まれる markup が実行されない。`<img src=x onerror=alert(1)>` を入力してもスクリプトが動作しない
- NFR-2.2: 外部ネットワークへの通信を一切行わない。入力内容がブラウザ外に出ない

### NFR-3: 可搬性・保守性

- NFR-3.1: `file://` で単一の HTML を開くだけで全機能が動作する。ビルド、サーバ、パッケージインストールを必要としない
- NFR-3.2: 実行時の外部依存（CDN、フォント、スクリプト）がゼロ
- NFR-3.3: 正規表現の評価ロジックとハイライトのセグメント生成が DOM に依存せず、DOM なしで単体テストできる
- NFR-3.4: Chromium 系の最新安定版で動作する

### NFR-4: 使い勝手

- NFR-4.1: パターン、テスト文字列、置換文字列、フラグ、結果表示が 1 画面に収まり、入力と結果を見比べるためのページ遷移が発生しない
- NFR-4.2: エラー、マッチなし、打ち切りの各状態が、通常の成功状態と区別できる形で表示される

## Constraints & Assumptions

### 技術制約

- C-1: 依存ゼロの素の HTML / CSS / JavaScript のみ。npm パッケージ、CDN、ビルドツールを使わない
- C-2: 正規表現エンジンはブラウザ組み込みの `RegExp` を使う。独自実装しない
- C-3: モジュール分割は ES Modules で行う。ただし `file://` での ES Modules 読み込みは CORS 制約を受けるため、実装方式の選定は epic の Architecture Decisions で確定させる
- C-4: 自動テストはプリインストール済みの Playwright + Chromium で実行する。追加のパッケージインストールを必要としない
- C-5: バックエンドを持たない。サーバサイドのコードを書かない

### 前提

- A-1: 利用者のブラウザは Chromium 系の最新安定版で、`RegExp` の名前付きグループと `s` / `u` フラグをサポートする
- A-2: 利用者は正規表現の基本構文を既に知っている（学習支援はスコープ外のため）
- A-3: テスト文字列は人間が手で貼る規模（数万文字以下）を想定する。巨大ログの解析用途は想定しない
- A-4: 単一利用者のローカル環境で動く。同時編集や共有は想定しない

## Out of Scope

以下は明示的に作らない。

- **OOS-1: JavaScript 以外の正規表現方言のサポート。** PCRE、Python `re`、Go `regexp`、.NET などの方言差は扱わない。ブラウザの `RegExp` の挙動のみを正とする。方言変換や互換性警告も出さない
- **OOS-2: AI によるパターン生成・添削。** 自然言語からの正規表現生成、パターンの説明文の自動生成、改善提案を行わない。ブラウザ単体・依存ゼロ・外部通信なしの制約と根本的に両立しない
- **OOS-3: 共有 URL / パーマリンク。** 入力状態を URL にエンコードして他者に共有する機能は作らない。永続化は localStorage による同一ブラウザ内の復元に限る
- **OOS-4: チートシート / 構文解説。** メタ文字一覧、量指定子の解説、サンプルパターン集といった学習者向けコンテンツは持たない。想定ユーザーを「構文を既に知っている開発者」に絞る
- **OOS-5: ReDoS 検出と性能計測の表示。** 破滅的バックトラッキングの静的検出や、マッチ所要時間のベンチマーク表示は行わない。ただし FR-1.3 / FR-1.5 の無限ループ・件数上限による防御は機能要件として実装する（暴走を防ぐことと、暴走を診断して見せることを区別する）
- **OOS-6: 複数パターンの同時比較。** 2 つのパターンを並べて差分を見るビューは作らない
- **OOS-7: マッチ結果のエクスポート。** CSV / JSON でのダウンロード機能は作らない
- **OOS-8: テーマ切替・設定画面。** ダークモードの手動切替や設定の永続化 UI は作らない

## Dependencies

### 外部依存

なし。実行時の外部依存はゼロ（NFR-3.2）。

### 開発時の依存

- D-1: Chromium（`/opt/pw-browsers/chromium` にプリインストール済み）— E2E テストの実行環境
- D-2: Playwright（プリインストール済み、`PLAYWRIGHT_BROWSERS_PATH=/opt/pw-browsers`）— E2E テストのドライバ
- D-3: `git` / `gh` CLI — CCPM の GitHub 同期に使用

### 内部依存

- D-4: 評価ロジック（FR-1）が、ハイライト描画（FR-2）、グループ表（FR-3）、置換プレビュー（FR-5）の全ての前提になる。評価ロジックの出力データ構造を最初に確定させる必要がある
- D-5: 永続化（FR-6）は他の機能から独立しており、並行して実装できる
