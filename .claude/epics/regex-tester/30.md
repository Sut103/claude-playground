# Task: ハイライト範囲の算出

## Description

マッチ配列と元のテスト文字列から、描画層がそのまま順に DOM 化できる `Segment[]` を組み立てる純粋モジュール `src/logic/highlight.js` を実装する。

「どこを塗るか」の判断をロジック層に閉じ込めるのが狙いである。UI 層は返ってきたセグメントを機械的に要素へ変換するだけになり、描画のテストがロジックのテストに置き換わる。

## Acceptance Criteria

- [ ] `src/logic/highlight.js` が `toSegments(input, matches)` を export し `Segment[]` を返す
- [ ] マッチのない領域が `kind:"text"` のセグメントとして出力される
- [ ] マッチ領域が `kind:"match"` として出力され、`matchIndex` が `matches` 配列への添字を指す
- [ ] セグメントを順に連結すると元の `input` に完全一致する（ゼロ幅セグメントは長さ 0 として寄与）
- [ ] ゼロ幅マッチが `kind:"zero-width"`、`value:""` として、正しい位置に挿入される
- [ ] マッチが 0 件のとき、入力全体を含む単一の `text` セグメントが返る
- [ ] 空文字列の入力に対して空配列、または空の `text` セグメントを返す（どちらかに決めてテストで固定）
- [ ] 隣接するマッチ（間に文字がない）で、空の `text` セグメントを挟まない
- [ ] 入力先頭・末尾にマッチがある場合に、余分な空セグメントが出ない
- [ ] `test/highlight.test.js` が上記を網羅し `node --test` で通る

## Technical Details

**シグネチャ**:

```js
/**
 * @param {string} input
 * @param {import("./types.js").MatchResult[]} matches
 * @returns {import("./types.js").Segment[]}
 */
export function toSegments(input, matches) {}
```

**前提**: `matches` は `start` 昇順で、範囲が重複しないものとして扱ってよい（`matcher.js` がその形で返す）。防御的に重複を検出した場合の挙動を決め、テストに残すこと。

**交互配色は UI 層の責務**: このモジュールは色を決めない。`matchIndex` の偶奇を見て UI が 2 色を割り当てる。ロジックに色の概念を持ち込まないこと。

**ゼロ幅の位置**: `start === end` のマッチは、その位置に幅を持たないマーカーとして挿入する。前後の `text` セグメントを分割することになるが、分割の結果として空の `text` を作らないよう注意する。

**禁止事項**: `document` / `window` / `localStorage` / `self` への参照を書かない。
