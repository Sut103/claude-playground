# Task: Fixtures and end-to-end acceptance tests

## Description

Build the Markdown fixture corpus and the end-to-end suite that proves all three PRD user stories against the assembled CLI. The unit tests from tasks 14–15 each cover one module in isolation; this task is the only place the whole pipeline runs against real files on disk, from argv through parsing, slugging, rendering, splicing, and writing.

Each test maps to a named acceptance criterion in the PRD rather than to an implementation detail, so the suite doubles as the evidence that the epic's success criteria are met. Story 1 checks that stdout generation leaves the source file untouched. Story 2 checks that `--in-place` rewrites only between the markers, preserves the surrounding bytes exactly, and is idempotent across two runs. Story 3 checks that `--check` returns 0 on a fresh fixture and 1 on a deliberately staled one, without ever writing.

Two error and edge paths get fixtures of their own: a document with no marker comments, which must exit 2 with the file untouched, and a document containing heading-like lines inside fenced code blocks, which must not appear in the TOC. The fenced-code fixture is the end-to-end counterpart to the parser's unit tests — it confirms the suppression survives the full pipeline rather than only the scanner.

Fixtures are copied into a temporary directory before any mutating test runs, so the committed fixtures stay pristine and the suite is re-runnable without a git checkout in between.

## Acceptance Criteria

- [ ] Story 1: `md-toc FIXTURE` prints a nested Markdown list to stdout, indented two spaces per level, with each entry linking to the heading's anchor.
- [ ] Story 1: after a default-mode run, the fixture file is byte-for-byte identical to before the run.
- [ ] Story 2: `--in-place` on a fixture replaces the content between `<!-- toc -->` and `<!-- /toc -->` with the generated TOC.
- [ ] Story 2: the bytes before the opening marker and after the closing marker are identical before and after `--in-place`.
- [ ] Story 2: running `--in-place` twice leaves the file byte-identical after the second run.
- [ ] Story 2: `--in-place` on the marker-less fixture exits 2, emits a message naming the expected markers, and leaves the file unmodified.
- [ ] Story 3: `--check` on a fixture whose embedded TOC is current exits 0.
- [ ] Story 3: `--check` on a deliberately staled fixture (a heading renamed after the TOC was written) exits 1 and names the stale file in its output.
- [ ] Story 3: the file is unmodified after `--check` in both the fresh and the stale case.
- [ ] Headings inside ``` and ~~~ fenced blocks in the fenced-code fixture are absent from the generated TOC.
- [ ] A fixture with duplicate heading text produces distinct anchors with numeric suffixes end to end.
- [ ] `python3 -m unittest discover` passes with zero failures across the whole suite.

## Technical Details

Owns exactly two paths:

- `tests/fixtures/`
- `tests/test_acceptance.py`

Fixture corpus under `tests/fixtures/`:

- `basic.md` — several nesting levels, marker comments present, embedded TOC already current; the Story 1 and Story 3-fresh fixture.
- `stale.md` — same document with one heading renamed after the TOC block was written; the Story 3-stale fixture.
- `no_markers.md` — headings but no marker comments; the error-path fixture.
- `fenced.md` — heading-like lines inside both ``` and ~~~ blocks, plus duplicate heading text for the anchor-suffix check.

`tests/test_acceptance.py` is a `unittest.TestCase` suite that drives `md_toc.cli.main(argv)` directly, asserting on the returned exit code, on `stdout`/`stderr` captured via `contextlib.redirect_stdout` / `redirect_stderr`, and on the file bytes read back with `Path.read_bytes()`. Each test copies the fixture it needs into a per-test `tempfile.TemporaryDirectory` via `shutil.copy`, so mutating runs never touch the committed corpus.

Byte-for-byte assertions compare `read_bytes()` rather than `read_text()`, so line-ending and trailing-newline regressions are caught rather than normalized away. The idempotency test snapshots the bytes after run one and asserts equality after run two.

Standard library only — `unittest`, `tempfile`, `shutil`, `pathlib`, `contextlib`.

## Dependencies

Tasks 13 and 15 must both land first, and this is the one task in the epic that cannot start early. It exercises the assembled CLI, so it needs the argparse surface, the file I/O, and the exit-code contract from 15, and the marker splicing plus the marker-absence error from 13. The Story 2 and Story 3 tests are precisely the tests of the seam between those two tasks — the point where `--in-place` and `--check` must agree because they share `splice_toc`. Nothing can be verified there until both halves exist.

Because it depends on the two tasks of the second parallel pair, it is marked `parallel: false` and is the final step on the critical path.
