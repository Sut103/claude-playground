# Bug: --in-place destroys CRLF line endings

## Context
Found by the acceptance suite in issue #17, which drives the assembled CLI over
real fixture files. Unit tests missed it because every module below the CLI
operates on already-decoded strings.

## Description
`md_toc/cli.py` reads with `Path.read_text(encoding="utf-8")`, whose universal
newline handling turns every `\r\n` into `\n`, and writes back with
`Path.write_text`, which emits `\n` on Linux. On a CRLF document every byte
outside the markers changes, and the file is rewritten even when the TOC was
already current.

This violates a named PRD Story 2 criterion: "Content outside the markers is
byte-for-byte unchanged."

## Steps to Reproduce
```
printf '# A\r\n\r\n<!-- toc -->\r\n- [A](#a)\r\n<!-- /toc -->\r\n' > crlf.md
python3 -m md_toc --in-place crlf.md
python3 -c "print(open('crlf.md','rb').read())"
```

## Expected vs Actual
- Expected: `b'# A\r\n\r\n<!-- toc -->\r\n- [A](#a)\r\n<!-- /toc -->\r\n'`
- Actual: `b'# A\n\n<!-- toc -->\n- [A](#a)\n<!-- /toc -->\n'`

`--check` is unaffected — it compares two already-normalized strings, so no
false stale in either direction.
