# Task: 受け入れ確認 — Success Criteria の検証

## Description

エピックの **Success Criteria (Technical)** を 1 項目ずつ検証し、それぞれについて「合格した根拠」を記録する。

これはコーディングタスクではない。新機能は実装しない。検証の結果、未達の項目が見つかった場合は**修正を直接行わず**、何がどう不足しているかを具体的に記録し、修正対象タスクへ差し戻す（あるいは新規タスクとして起票する）。検証と修正を同じタスクで混ぜると、「検証したから通ったのか、直したから通ったのか」が曖昧になる。

検証は 3 つの性質に分かれる。

1. **自動テストの確認** — pytest の実行結果
2. **カバレッジの突き合わせ** — US-1〜US-5 の各 Acceptance Criteria が、どのテスト関数で担保されているかの対応付け
3. **機械的・手動の確認** — 実ターミナルでの通し実行、および import の grep 検査

## Acceptance Criteria

- [ ] **テスト全件パス** — リポジトリルートで `python -m pytest` を実行する。**合格条件: 失敗 0 件・エラー 0 件で終了し、終了コードが 0 である。** 収集されたテスト件数を記録する。skip があれば、その理由を 1 件ずつ記録する（無言の skip は未達扱いとする）

- [ ] **受け入れ基準とテストの対応表を作る** — PRD の US-1〜US-5 に列挙された Acceptance Criteria をすべて洗い出し、各項目に対応するテスト関数を `ファイル::関数名` の形で対応付けた表を作る。**合格条件: 全項目に少なくとも 1 つのテストが紐づいており、紐づかない項目が 0 件であること。** 紐づかない項目があった場合は「未カバー」として明示的に列挙し、担当タスクへ差し戻す（表から黙って落とさない）

- [ ] **対応付けの妥当性を確認する** — 表に挙げたテストが、名前だけでなく**実際にその受け入れ基準を検証しているか**を中身を読んで確かめる。**合格条件: 各テストのアサーションが、対応付けた受け入れ基準の主張と一致していること。** 名前は合っているが実質を検証していないテストは未カバーとして扱う

- [ ] **実ターミナルでの通し実行** — クリーンな一時ディレクトリ（`mktemp -d`）に移動し、`TASK_CLI_FILE` を設定したうえで、`add` → `list` → `done` → `list --all` → `rm` を**実際にシェルから順に実行**する。**合格条件: 各ステップの標準出力が期待どおりで、`echo $?` がすべて 0 であること。** 実行したコマンドと得られた出力をそのまま記録する。E2E テストが通っていることは代替にならない（Success Criteria 2 が「実際のターミナル実行での確認」を要求している）

- [ ] **生成された Markdown の目視確認** — 上の通し実行で生成された `TASKS.md` の中身を表示する。**合格条件: `- [ ]` / `- [x]` のチェックリスト行として妥当で、メタデータ記法が可読性を壊しておらず、人間が手編集できる形であること**（US-2、NFR-5）

- [ ] **手編集との往復を実地で確認** — 上の `TASKS.md` に見出し行と自由記述行を手で追記し、タスク行を並べ替えたうえで、`list` と `add` を実行する。**合格条件: `list` が全タスクを引き続き読め、追記した見出し行と自由記述行が操作後もファイルに残っていること**（Success Criteria 4、AD-3）

- [ ] **標準ライブラリのみであることの機械的確認** — `taskcli/` 配下の全 `.py` について import 文を grep で抽出する（例: `grep -rnE '^\s*(import|from)\s+' taskcli/`）。抽出結果を、`sys.stdlib_module_names` および `taskcli` 内部モジュールの一覧と突き合わせる。**合格条件: どちらにも属さないモジュール名が 0 件であること**（NFR-1）。`tests/` 配下の pytest import は開発時依存として許容範囲であり、この検査の対象外とする

- [ ] **往復テストの存在確認** — `parse_line` と `format_line` の往復で情報が失われないことを検証するテストが存在し、パスしている。**合格条件: 該当テストを `ファイル::関数名` で特定でき、優先度・タグ・期限を持つケースと持たないケースの両方をカバーしていること**

- [ ] **検証結果の記録** — 上記すべての項目について、実行したコマンド・得られた出力・判定（合格／未達）をまとめて報告する。**合格条件: エピックの Success Criteria (Technical) の全チェックボックスに判定が付いており、未判定の項目が残っていないこと**

- [ ] **未達項目の扱い** — 未達が 1 件でもあれば、このタスクは「未達あり」として報告し、該当箇所を修正するタスクを特定する。**このタスク内でプロダクションコードを修正しない**

## Technical Details

**なぜ実ターミナル実行を別途行うのか.** 006 の E2E テストは `subprocess` 経由なので実行環境にかなり近いが、`env` を明示的に組み立てており、`PYTHONPATH` やカレントディレクトリの前提がテストコードに埋め込まれている。素のシェルから叩いたときに動かない、というズレはこの層でしか見つからない。PRD の Success Criteria 2 が「実際のターミナル実行での確認」と書いているのはこの区別のためである。

**import 検査の進め方.** grep で `import` / `from` 行を機械的に抜き出し、モジュール名部分だけを取り出す。判定は目視ではなく `sys.stdlib_module_names`（Python 3.10+ で利用可能）との集合演算で行うと取りこぼしがない。相対 import（`from .parser import Task`）は内部モジュールとして除外する。関数内の遅延 import も grep に引っかかるので、行頭の空白を許すパターンにしておく。

**対応表の形.** US 番号・受け入れ基準の本文・テストの `ファイル::関数名`・判定、の 4 列で十分である。「1 つのテストが複数の基準をカバーする」「1 つの基準に複数テストが対応する」のどちらもあり得るので、多対多を許す形にする。

**判定の粒度.** 「だいたい動いている」を合格にしない。各項目に明示した合格条件を満たすかどうかだけで判定する。曖昧な場合は未達側に倒し、根拠を書く。

## Dependencies

- Python 3.10 以上（`sys.stdlib_module_names` の利用に必要、NFR-2）
