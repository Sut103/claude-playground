# Bug: an ATX heading inside the marker region breaks idempotency

## Context
Found by the acceptance suite in issue #17. Low severity — contrived input, and
the document converges after the second run.

## Description
`extract_headings` scans the entire file, including the marker region that is
about to be overwritten. A heading written inside that region is therefore
collected into the TOC by the first run and destroyed by the same splice, so the
second run produces a different TOC.

This is a genuine violation of the PRD's "running the command twice in a row
produces no change on the second run", though it requires a heading to be
authored inside the managed region in the first place.

## Steps to Reproduce
```
printf '# A\n\n<!-- toc -->\n# Ghost\n<!-- /toc -->\n\n## B\n' > inside.md
python3 -m md_toc --in-place inside.md   # TOC contains A, Ghost, B
python3 -m md_toc --in-place inside.md   # TOC contains A, B
```

## Expected vs Actual
- Expected: the second run is a no-op
- Actual: the second run removes the `Ghost` entry

## Acceptance Criteria
- [ ] Headings inside the marker region are excluded from extraction, so the
      first run is already stable
- [ ] Headings outside the region are unaffected
- [ ] A document with no markers is unaffected in stdout mode
- [ ] A regression test covers the heading-inside-region case
- [ ] `python3 -m unittest discover` passes with zero failures
