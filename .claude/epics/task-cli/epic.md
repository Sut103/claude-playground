# Epic: task-cli

## Overview

Markdown ファイルを唯一のデータストアとするタスク管理 CLI を、Python 標準ライブラリのみで実装する。

構造は 3 層に分ける。**パーサ層**が Markdown 行と `Task` オブジェクトを相互変換し、**ストア層**がファイルの読み書きと原子的置換を担い、**コマンド層**が argparse のサブコマンドとして利用者に露出する。層の境界を明確にすることで、パーサとコマンドを別々のエージェントが並行して実装できる。

## Architecture Decisions

### AD-1: 行フォーマット — GFM チェックリスト + 末尾メタデータ

タスク 1 件を 1 行で表す。ID とメタデータは、GitHub 上でのレンダリングを壊さない形で埋め込む。

```markdown
- [ ] リファクタする `#3` `!high` `@docs` `@refactor` `~2026-08-20`
- [x] README を書く `#1` `!mid`
```

| 記号 | 意味 |
| --- | --- |
| `#N` | タスク ID |
| `!high` / `!mid` / `!low` | 優先度 |
| `@tag` | タグ（0 個以上） |
| `~YYYY-MM-DD` | 期限 |

**なぜこの形か。** 検討した代替は 2 つあった。

1. **YAML フロントマター + 本文** — 構造化は容易だが、1 タスク 1 行という Markdown チェックリストの利点が失われ、GitHub 上でチェックボックスとして表示されない。US-2 の受け入れ基準に反する
2. **HTML コメントにメタデータを隠す** — レンダリングは綺麗だが、人間が手編集する際に見えない情報ができてしまい、NFR-5（手編集できること）を損なう

バッククォートで囲むのは、レンダリング時にコード片として視覚的に区別され、かつ本文中に同じ記号が現れても衝突しにくいためである。

### AD-2: ID は単調増加、再利用しない

FR-5 の要求。ファイル内の既存 ID の最大値 + 1 を採番する。削除しても他タスクの ID は変わらない。ID の採番状態は別途保存せず、**毎回ファイル全体から導出する**。状態ファイルを増やさないことを優先した。

### AD-3: パーサは寛容、書き込みは厳格

FR-8 の要求。読み取り時は、パースできない行を警告して読み飛ばす。ただし**読み飛ばした行はファイルから消さない** — 書き戻し時に原文のまま保持する。手編集で入れたメモや見出しが CLI 操作で消える事態を防ぐ。

これは実装上、ストア層がファイルを「パース済みタスク行」と「そのまま維持する行」の混在リストとして保持することを意味する。

### AD-4: 書き込みは一時ファイル + `os.replace`

NFR-3 の要求。同一ディレクトリに一時ファイルを作り、書き込み後に `os.replace` で置換する。`os.replace` は同一ファイルシステム上で原子的であることが POSIX で保証されている。

### AD-5: 「今日」は注入可能にする

期限判定（OVERDUE / DUE TODAY）は現在日付に依存する。テストを日付非依存にするため、判定関数は `today` を引数で受け取り、既定値を `date.today()` とする。グローバルなモンキーパッチを避ける。

## Technical Approach

> CCPM の epic テンプレートは Frontend / Backend / Infrastructure の 3 分割を想定しているが、本エピックは CLI ツールであり該当しない。実態に合わせて層で分割する。

### パーサ層 (`taskcli/parser.py`)

- `Task` データクラス: `id`, `text`, `done`, `priority`, `tags`, `due`
- `parse_line(line) -> Task | None` — AD-1 の書式を解釈する。該当しなければ `None`
- `format_line(task) -> str` — `Task` を行に戻す。往復で情報が失われないこと
- 優先度・日付の妥当性検証（`Priority` の列挙、`YYYY-MM-DD` の厳密パース）

### ストア層 (`taskcli/store.py`)

- `load(path) -> Document` — ファイル全体を読み、タスク行とその他の行を順序を保って保持する。パース失敗行は警告して非タスク行として扱う（AD-3）
- `save(path, document)` — AD-4 の原子的書き込み
- `next_id(document) -> int` — AD-2 の採番
- ファイルが存在しない場合は空の `Document` を返す（US-1 の受け入れ基準）

### コマンド層 (`taskcli/cli.py`)

- argparse のサブパーサとして `add` / `list` / `done` / `rm` を定義
- 各コマンドは終了コードを返す関数として実装し、`main()` がそれを `sys.exit` に渡す（FR-9）
- ファイルパス解決: `TASK_CLI_FILE` 環境変数 → 既定 `./TASKS.md`（FR-6）

### 表示層 (`taskcli/render.py`)

- `list` の出力整形。並び順は優先度降順 → 期限昇順 → 期限なしが末尾（US-3）
- `OVERDUE` / `DUE TODAY` の付与（US-4、AD-5）
- カラーなし・プレーンテキストのみ（Out of Scope）

### テスト (`tests/`)

- US-1 〜 US-5 の各 Acceptance Criteria に対応するテストを置く
- `tmp_path` フィクスチャで実ファイルを使い、モックを避ける

## Implementation Strategy

**並列化の考え方.** パーサ層は他のどの層にも依存しないため最初に確定させる。パーサが決まれば、ストア層・表示層・コマンド層は互いのファイルを触らずに並行実装できる。

依存の形は次のとおり。

```
[T1 プロジェクト初期化]
        │
[T2 パーサ層]  ← ここが全体のクリティカルパス
        │
   ┌────┼────┐
[T3]  [T4]  [T5]        ← 並列可能（触るファイルが重ならない）
ストア 表示  コマンド骨格
   └────┼────┘
        │
[T6 コマンド結線とE2E]
        │
[T7 受け入れ確認]
```

**リスクの置き方.** 最も設計判断の多い AD-1（行フォーマット）を T2 に集中させ、そこを通過すれば残りは機械的になるようにした。T2 で書式が変われば T3〜T5 は全部やり直しになるため、T2 を並列化しない。
